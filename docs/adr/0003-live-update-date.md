# 0003. Live 歌單更新日期基準點決策

## 狀態
已接受 (Accepted)

## 上下文
我們探討了當使用者忘記在換歌單當天更新 Bot，是否需要支援自訂日期回溯的功能。

## 決策
我們決定**不引入自訂日期或日期補記的功能，統一以 Bot 接收到 `/update_live` 指令的當天 (今天) 作為歌曲變更日期。**

根據使用者習慣分析，使用者只有在「歌單有更新的當天」才會想要操作 Bot 來記錄這件事；在歌單沒有變動的日常，使用者不會來操作 Bot。因此，Bot 收到更新請求的日期，即為實質上的「歌單變更日期」。

維持此設計能使使用者介面最簡潔，使用者不需要在每行歌單或指令後方手動加註日期，大幅降低了操作負擔。

## 後果
- **優點**：
  - 保持指令格式極簡（只需發送歌單文字）。
  - 簡化 Bot 解析器邏輯，不需處理各種日期格式輸入。
  - 符合直覺的「有變動才上來更新」的使用習慣。
- **缺點**：
  - 若使用者確實延遲了數天才上來更新 Bot，歷史紀錄的啟用/停用日期會與真實日期產生數天的誤差。但對於 Zumba 歌單管理而言，數天的誤差並不影響「這首歌在某期 ZIN 的使用狀態」統計，因此在商業邏輯上完全可以接受。
