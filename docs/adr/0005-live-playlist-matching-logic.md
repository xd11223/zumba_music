# 0005. Live 歌單集合比對與精簡原則決策

## 狀態
已接受 (Accepted)

## 上下文
我們對 Live 歌單的「比對更新機制」在極端實務情境下進行了邊界案例評估，包括：
1. **同一天多次更新（排錯歌單）**：可能產生同一天內啟用又停用的歷史雜訊。
2. **主題課/臨時代課歌單**：只使用一天的非常駐歌單，是否會造成歷史紀錄中斷破碎。
3. **歌曲重複與順序**：同一份歌單中歌曲出現兩次，或需要記錄歌曲在當天播放的順序。

## 決策
我們決定**維持使用最精簡的「無序集合比對 (Set Difference)」演算法**，不做額外的複雜邏輯包裝：
1. **無效歷史處理**：若使用者在同一天多次操作導致產生當日起訖的無效歷史，系統不進行自動防呆刪除，維持資料庫紀錄，由使用者於操作端自行避免或容忍此微小誤差。
2. **主題課情境**：依據使用者業務規則，主題課或特別節日的臨時歌單不屬於常駐 Live 歌單，使用者不會將其更新至 Bot 中，因此不會影響 active 歷史。
3. **歌曲重複與順序**：系統不記錄歌曲順序與單次歌單中的重複次數，僅記錄「歌曲是否處於 active 使用中」的狀態。

維持此設計能避免將過多的狀態判定（如同一天多次更新的邏輯判定）寫入 Go 程式，保持資料庫 Schema 與更新程式碼的極簡與高效。

## 後果
- **優點**：
  - 資料庫與更新程式碼維持最高穩定度。
  - 運算速度極快，佔用空間極小。
- **缺點**：
  - 無法還原出歷史上某一天歌單的精確歌曲播放順序，但在 Zumba 歌單管理的情境下此功能並無業務價值，因此此限制完全合理。
